## Latest Projects

### 1. [Terraform AWS Multi-Environment Infrastructure](https://github.com/mishra0703/terraform-aws-multi_env-infra)

[![Terraform](https://img.shields.io/badge/Terraform-7B42BC?style=flat&logo=terraform&logoColor=white)](https://terraform.io)  [![AWS EC2](https://img.shields.io/badge/AWS_EC2-FF9900?style=flat&logo=amazonaws&logoColor=white)](https://aws.amazon.com/ec2/)  [![AWS S3](https://img.shields.io/badge/AWS_S3-569A31?style=flat&logo=amazons3&logoColor=white)](https://aws.amazon.com/s3/)  [![DynamoDB](https://img.shields.io/badge/DynamoDB-4053D6?style=flat&logo=amazondynamodb&logoColor=white)](https://aws.amazon.com/dynamodb/)

**Multi-environment AWS infrastructure provisioned with Terraform workspaces and reusable modules.** A single codebase manages both dev and prod environments — no copy-pasting, no drift.

**Key highlights:**
- Designed a `locals` config map in `main.tf` that drives resource counts per workspace — adding a new environment (e.g. staging) requires a single map entry, nothing else
- Modular structure across EC2, S3, and DynamoDB — each module is independently reusable and accepts workspace-specific counts via `count`
- All resources are workspace-prefixed (`dev-terra-server-1`, `prod-terra-server-2`) to eliminate naming conflicts across environments
- Verified end-to-end: provisioned 3 EC2 instances, 2 S3 buckets, and 2 DynamoDB tables in prod — outputs surfaced all ARNs and IPs cleanly

### 2. [Kubernetes WordPress Capstone](https://github.com/mishra0703/k8s-wordpress-capstone)

[![Kubernetes](https://img.shields.io/badge/Kubernetes-326CE5?style=flat&logo=kubernetes&logoColor=white)](https://kubernetes.io)  [![Docker](https://img.shields.io/badge/Docker-2496ED?style=flat&logo=docker&logoColor=white)](https://docker.com)  [![Helm](https://img.shields.io/badge/Helm-0F1689?style=flat&logo=helm&logoColor=white)](https://helm.sh)  [![MySQL](https://img.shields.io/badge/MySQL-4479A1?style=flat&logo=mysql&logoColor=white)](https://mysql.com)

**Production-style WordPress + MySQL deployment on Kubernetes — hand-written manifests, no shortcuts.** Built to consolidate real K8s skills: StatefulSets, headless Services, HPA, probes, persistent storage, and a Helm comparison.

**Key highlights:**
- MySQL deployed as a StatefulSet with a headless Service — WordPress resolves the pod via stable DNS (`mysql-app-0.mysql-svc.capstone.svc.cluster.local`) with zero hardcoded IPs
- Credentials managed via Kubernetes Secrets; non-sensitive config via ConfigMaps — clean separation between config and secrets
- HPA configured to scale WordPress pods from 2 to 10 replicas at 50% CPU — load-tested with an in-cluster busybox loop and watched the scaler react in real time
- Self-healing verified: deleted both WordPress and MySQL pods manually — Deployment replaced the WordPress pod seamlessly, StatefulSet reattached MySQL to its PVC with no data loss, recovery in ~5–10 seconds
- Helm comparison included: surfaced real-world registry issues with Bitnami's August 2025 restructuring — documented the failure, diagnosed the cause, and drew concrete trade-offs between hand-written manifests vs. third-party charts
